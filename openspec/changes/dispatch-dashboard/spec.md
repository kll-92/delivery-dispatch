# 功能规范：配送调度后台

## 1. 页面结构

系统至少包含以下页面区域：

1. 总览页：显示骑手总数、可用骑手数、订单总数和待派单数。
2. 骑手页：显示骑手编号、姓名、手机号、状态、当前位置和当前订单数。
3. 订单页：显示订单编号、订单状态、骑手、取货地址、收货地址和更新时间。
4. 调度操作区：允许对订单进行自动派单、手动指定骑手、开始配送、完成和取消。

## 2. 骑手行为

- 页面加载时调用 `GET /api/v1/riders` 获取骑手列表。
- 点击骑手详情时调用 `GET /api/v1/riders/{id}`。
- 输入经纬度、半径和数量后调用 `GET /api/v1/riders/nearby` 查询附近骑手。
- 请求失败时显示可读的错误提示，不显示原始堆栈。

## 3. 订单行为

- 页面加载时调用 `GET /api/v1/orders` 获取订单列表。
- 创建订单调用 `POST /api/v1/orders`。
- 自动派单调用 `PATCH /api/v1/orders/{orderId}/dispatch`。
- 手动派单调用 `PATCH /api/v1/orders/{orderId}/assign/{riderId}`。
- 状态操作分别调用 `start-delivery`、`complete` 和 `cancel` 接口。
- 操作成功后刷新对应订单，避免页面显示旧状态。

## 4. 验收场景

### 场景 A：正常查看

- 给定后端正常运行，页面可以加载骑手和订单列表。
- 列表中的状态使用中文标签和颜色区分。

### 场景 B：派单成功

- 用户点击自动派单。
- 页面显示处理中状态，避免重复点击。
- 后端返回成功后，订单显示已派单及对应骑手。

### 场景 C：后端异常

- 后端不可用或返回错误时，页面保留已有数据并显示失败提示。
- 用户可以重新点击重试。

### 场景 D：无数据

- 列表为空时显示明确的空状态，而不是空白页面。
