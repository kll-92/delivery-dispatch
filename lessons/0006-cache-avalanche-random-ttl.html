第四个实战问题：大量缓存一起过期

假设系统在同一时刻把一批骑手详情都以 10 分钟 TTL 写入 Redis。10 分钟后，它们可能同时失效；大量请求会同时回源 MySQL，造成连接池和数据库瞬时压力。

缓存雪崩 ≠ 缓存穿透

  • 缓存穿透：请求不存在的数据，缓存无法保存正常结果。
  • 缓存雪崩：许多原本存在的缓存，在相近时刻集体失效或 Redis 故障。

第一层防护：随机 TTL

固定 TTL：全部 600 秒 → 可能一起过期
随机 TTL：600～660 秒 → 过期时间分散，回源压力被摊开

随机 TTL 不会让缓存永不失效；它不能解决 Redis 整体宕机，也无法完全处理同一个热点 Key 的高并发回源。后续会学习互斥锁与逻辑过期。

本项目的改动

将正常骑手详情从固定 10, TimeUnit.MINUTES 改为：基础 600 秒，加 0～60 秒随机值。

Redis 官方 Cache Aside 文档指出，热门 Key 到期时可能有大量进程同时回源，形成 cache stampede；TTL 限制缓存存活，额外策略用于控制到期并发。Redis 官方 Cache Aside
