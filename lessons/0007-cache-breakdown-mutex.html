第五个实战问题：一个热点骑手详情过期

假设骑手 1 正在配送热门订单，几千个页面同时查看 GET /api/v1/riders/1。当 rider:detail:1 正好过期，几千个请求都发现 Redis 未命中，并同时查询 MySQL。这叫缓存击穿，也常叫热点 Key 失效后的 cache stampede。

它和缓存雪崩有什么不同？

  • 雪崩：许多 Key 大批量失效，范围广。
  • 击穿：一个或少数热点 Key 失效，但同一 Key 的并发量极大。

互斥锁的思路

请求 A：发现 rider:detail:1 未命中 → 获得 rebuild:lock:rider:1 → 查 MySQL → 回填缓存 → 释放锁
请求 B：发现同一 Key 未命中 → 未获得锁 → 短暂等待 → 再查 Redis
                                      └→ A 已回填：直接返回缓存

目标不是让所有请求排队查 MySQL，而是只允许一个请求重建缓存，其他请求等它写完后读缓存。

锁为什么必须有 TTL？

如果获得锁的服务在查询中崩溃，锁若永不过期，后续所有请求都会一直拿不到锁。我们会使用 Redis 的原子命令：SET lockKey token NX EX 10，即“仅当锁不存在时写入，并在 10 秒后自动过期”。

本项目实现边界

本地单实例项目先学习正确的基础流程：获取锁、双重检查缓存、回填、finally 释放锁。生产多实例还必须用唯一 token 校验“锁是否仍属于自己”再删除，避免误删其他实例的锁；后续会补这一层。
