第十四课：Actuator 配置到底补了什么

这不是新的业务功能，而是给正在运行的 Spring Boot 应用加一扇“观察窗”：看服务是否健康、有哪些指标、接口请求是否变慢。

先不要怕“端点”这个词

你之前在 Swagger 里调用过 GET /api/v1/riders/1。这个地址就是一个“端点”：可以把它理解成应用对外开放的一个窗口。有人访问这个窗口，应用就按约定做一件事，并返回结果。

例如，/api/v1/riders/1 是“查询 1 号骑手”的业务窗口；它和订单、骑手这些业务有关。

“管理端点”到底是什么意思

这里的“管理”不是“管理订单”，也不是让你手动操控服务器。它只是指：给开发者、运维人员看的应用检查窗口，用来回答“程序现在还好吗”。

可以把正在运行的配送系统想成一辆车：

现实里的东西项目里的地址它回答什么
看发动机故障灯/actuator/health应用还能不能正常工作
看仪表盘数据/actuator/metrics内存、请求次数等运行数据
看车辆资料/actuator/info应用版本、名称等自定义信息

所以，“管理端点”可以先记成一句话：不是业务接口，而是给人检查和了解应用状态的接口。

/actuator/health 被访问时发生了什么

你在浏览器打开这个地址时，过程可以按下面理解：

浏览器发出 GET /actuator/health
        ↓
Tomcat 收到请求
        ↓
Spring Boot Actuator 认出这是“健康检查窗口”
        ↓
检查应用自己，以及已经启用的数据库、Redis 等资源
        ↓
返回一小段 JSON

最简单的返回可能是：

{"status":"UP"}

UP 就是“目前看起来可以工作”。如果某个必要资源不可用，可能返回 DOWN 或 OUT_OF_SERVICE。如果整个 Java 应用已经挂掉，连这个地址都访问不到，因为没有程序来接收请求。

第一步：依赖让功能进入项目

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

这个 starter 把 Spring Boot Actuator 及其自动配置放入应用。它不是另一个 HTTP 服务器，也不会替代你写的 Controller；它会帮应用准备一组“自检接口”。

第二步：配置决定哪些端点能通过 HTTP 访问

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics

当前配置只允许下面三个自检接口通过 HTTP 访问：

地址用途
/actuator/health应用和它需要的资源是否处于可用状态
/actuator/info应用自定义信息
/actuator/metrics列出应用已记录的指标名称

Spring Boot 文档明确提醒：管理端点可能包含敏感信息，暴露前要考虑防护；这里只用于本地学习，不能直接无鉴权开放到公网。详见官方 Actuator 文档。

metrics 不是一个神奇的性能结论

访问：

GET http://localhost:8080/actuator/metrics

通常先得到指标名称列表，再查看具体指标：

GET /actuator/metrics/jvm.memory.used
GET /actuator/metrics/jvm.gc.pause
GET /actuator/metrics/http.server.requests

它可以帮助回答“当前内存使用多少”“是否有 GC 暂停”“HTTP 请求是否有计数和耗时”等观察问题，但不能仅凭一次访问就声称系统吞吐量、性能提升比例或线上稳定性。Spring Boot 的 metrics 端点本意是诊断当前已记录的指标，不是完整的生产监控后端。

为什么改完 yml 要重启？

application.yml 是应用启动时加载进 Spring Environment 的配置。IDEA 里已经运行的 JVM 不会自动重新读取你刚保存的文件，所以旧进程仍可能只暴露原来的 health,info：

修改 application.yml
        ↓
停止旧的 Spring Boot 运行进程
        ↓
重新启动应用
        ↓
新配置才进入当前 JVM

这件事和 Docker 中的 MySQL、Redis 容器不是一回事：这里只需要重启 IDEA 里的 Spring Boot 应用，不需要删除或重建容器。

它和 JVM 学习怎样串起来？

Actuator 观察到现象：接口慢 / 堆使用高 / GC pause 增长
        ↓
再用 jps 找 Java 进程
        ↓
用 jcmd 查看堆和线程
        ↓
结合日志与请求情况定位原因

所以 Actuator 是“先看症状”的工具，不是“自动调优 JVM”的工具。真正调优前要先有指标、现象和可复现实验。
