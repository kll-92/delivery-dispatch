第三个实战问题：查不存在的骑手会怎样？

假设有人反复请求 GET /api/v1/riders/999999。这个 ID 在 Redis 没有，在 MySQL 也没有。若每次都直接抛“骑手不存在”，每一个请求都会穿过 Redis 打到 MySQL。

这叫缓存穿透

请求不存在的 id
  ↓
Redis 未命中
  ↓
MySQL 也查不到
  ↓
直接返回异常（没有留下任何缓存）
  ↓
下一次相同请求，重复访问 MySQL

缓存穿透不是“Redis 被穿透了”，而是缓存挡不住无效请求，数据库成了每次请求的终点。

本项目的第一层解法：空值缓存

Redis 未命中
  ↓
MySQL 查不到 rider
  ↓
Redis SET rider:detail:999999 "" EX 60
  ↓
返回“骑手不存在”

下一次相同请求
  ↓
Redis GET 得到空字符串
  ↓
直接返回“骑手不存在”，不查 MySQL

两个容易混淆的“空”

  • null：Redis 没有这个 Key，即真正的缓存未命中。
  • ""：Redis 有这个 Key，但值是我们专门写进去的“数据库不存在”标记。

因此，代码不能再只用 StringUtils.hasText(cacheJson) 判断。它会把 "" 与 null 都当成“没有有效文本”，从而又查一次 MySQL。

为什么空值 TTL 要短？

若管理员随后真的创建了 id=999999 的骑手，空缓存不能长时间挡住新数据。因此本项目让空值只缓存 60 秒；正常骑手详情仍缓存 10 分钟。

与布隆过滤器的关系

空值缓存适合当前项目：改动小、能保护重复的无效请求。布隆过滤器适合海量、随机且恶意的 ID 攻击，但有误判概率，下一阶段再学。

官方 Cache Aside 文档说明：缓存未命中会回源主库并回填，TTL 用于限制缓存数据的存活时间；空值缓存正是针对“不存在记录反复回源”的补充策略。Redis 官方 Cache Aside
