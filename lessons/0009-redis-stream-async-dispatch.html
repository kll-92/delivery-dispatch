第九课：Redis Stream 如何把派单从接口中拆出去

历史课程：2026-09-27 项目的异步通道已迁移到 RocketMQ。本页用于复习 Stream 思路，不再代表当前运行代码。

目标：让“创建订单”快速完成，让后台可靠地执行距离匹配与原子派单。

同步派单的压力在哪里？

创建订单 → GEO 查附近骑手 → MySQL 原子占用 → 更新订单 → 返回

订单高峰时，每个 HTTP 请求都要等待派单链路；如果某一步慢，接口就慢。

先弄懂 Outbox 是什么

Outbox 字面上是“发件箱”。在这个项目里，它不是 Redis、不是 Spring 的某个类，而是 MySQL 里的一张表：暂存“本服务已经决定要发出去，但还没确认送到 Redis”的业务事件。

例如创建订单后，这张表里会有一条记录：orderId=42、eventType=DISPATCH_REQUEST、status=0（待投递）。可以把它想成订单仓库旁的发件托盘：订单记录是业务档案，Outbox 记录是要寄出的派单小票。

Outbox 的作用是什么

订单存在 MySQL，派单事件写 Redis Stream，是两套系统的两次写入。若订单提交后 Redis 暂时不可用，订单存在但派单事件会丢失；若先写 Redis、再写订单，订单回滚后消费者又会收到一条无效事件。

Transactional Outbox 的做法是：订单和“待投递事件”先在同一个 MySQL 事务中一起保存。Redis 故障不会丢掉这条数据库记录，后台发布器可以稍后重试。

本项目的异步链路

POST /orders
  → 一个 MySQL 事务：插入订单 + 插入 dispatch_outbox(status=0)
  → 提交：两条记录一起存在
  → HTTP 接口返回

DispatchOutboxPublisher（每 5 秒）
  → SELECT 待投递行 FOR UPDATE SKIP LOCKED
  → XADD stream:dispatch:events
  → Outbox 状态改为已投递（status=1）并提交

DispatchStreamConsumer（每 5 秒）
  → XREADGROUP 读取事件
  → GEO 候选 + MySQL 原子派单
  → 成功：XACK
  → 失败：不 ACK，保留在 Pending List

投递失败与重复投递

Redis 写入失败时，发布器不把 Outbox 标为已投递，下一轮继续尝试。若 Redis 已接收 XADD，但应用在标记 Outbox 前崩溃，重试可能再发一次。Outbox 因此保证事件不会轻易丢失，但投递语义仍是至少一次；订单状态检查负责让重复派单事件幂等。

FOR UPDATE SKIP LOCKED 是数据库行级领取方式：多个发布器可同时取不同的待处理行，被别的事务锁住的行会暂时跳过，不需要锁整张表。它要求查询在事务中运行。参见 MySQL 锁定读文档。

Pending 的意思：消费者已经收到这条消息，但 Redis 还没收到“处理完成”的 ACK。它不等于“新消息没人拿”，也不一定代表报错——消费者可能正在正常处理。ACK 会把它从 Pending 跟踪列表中移除，但不会因此删除 Stream 里的原始记录。

消费者宕机后，Pending 怎么恢复？

消息被消费者组读取后会挂在该消费者名下。若消费者崩溃且没有 ACK，消息不会自动变成新消息。本项目每 5 秒扫描 Pending，只对超过 30 秒没有进展的消息执行 claim，把消息转给当前消费者，再调用同一个处理方法。

Pending 扫描
  → 未超过 30 秒：先不抢，避免干扰正常处理
  → 超过 30 秒：claim 重新认领
  → 业务成功：XACK
  → 业务失败：不 ACK，下一轮继续重试

这仍然是至少一次投递，可能重复执行；订单状态检查会让已经派单的订单直接跳过，从而保证业务幂等。

三个命令

命令项目含义
XADD追加一张“订单 N 需要派单”的电子小票。
XREADGROUP派单消费者组领取自己的小票。
XACK派单成功后确认小票处理完成。

为什么还需要 MySQL 条件 UPDATE？

Stream 是至少一次投递：消费者可能在业务成功后、ACK 前崩溃，因此同一订单事件可能再次送达。消费者处理前会检查订单是否仍为待派单；实际占用骑手和更新订单仍由 MySQL 条件 UPDATE 保证。消息重复不等于订单重复派单。

当前实现的边界

这是单消费者教学实现，消费者名为 dispatch-worker-1；当前已经有超时 Pending 的 claim 恢复。Outbox 的重试暂时没有退避上限或死信队列，因此持续失败的记录会反复重试，这是后续可完善的生产化边界。

面试表达

订单创建事务同时落库订单和 Outbox 事件，由轮询发布器异步投递到 Redis Stream；消费者组执行 GEO 候选筛选与 MySQL 原子派单，成功后 ACK。Outbox 避免订单提交成功但消息丢失；订单状态条件更新保证重复投递下的幂等性。
