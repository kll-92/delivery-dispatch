第十一课：两种更新保护，分别防不同的并发问题

这节不重讲 Redis、Outbox 或事务基础，只把本轮新增的两类代码放到一起比较：订单状态条件更新，以及骑手资料只更新指定字段。

先回顾 第十课：为什么先查再改不够安全；项目总览见 项目知识总复习。

问题一：订单状态可能已经被别人改变

用户取消和后台派单同时处理一张“待派单”订单。两边都可能先读到状态 0，但读取后到写入前，另一边已经先完成了状态转换。

开始配送：只允许 1（已派单）→ 2（配送中）
取消订单：只允许 0（待派单）→ 4（已取消）

所以订单 Mapper 把“当前允许的状态”放进 WHERE：

UPDATE delivery_order
SET status = 4
WHERE id = 42 AND status = 0;

它不是“我以前查到状态 0，所以现在可以改”，而是“数据库执行这一刻，只有仍为 0 才允许改成 4”。若派单先把状态变为 1，取消更新就匹配不到该行，Mapper 返回 0；Service 提示状态已变化。开始配送同理：startIfAssigned 要求订单仍为 1，才写成 2。

Java 里的第一次状态校验仍有用：它负责快速拒绝明显不合法的请求、提供业务提示；SQL 条件负责挡住校验之后发生的竞态。MySQL/InnoDB 会协调对同一记录的更新，详见 InnoDB 锁官方文档。

问题二：整条骑手记录里有不属于资料编辑的字段

骑手资料请求可能只改姓名和手机号，但数据库记录里还包含接单数、骑手状态、坐标等业务数据。若先读出整条旧记录，再用 updateById(rider) 保存，读出的旧接单数/状态也可能被一起写回。

时间 T1：资料请求读到 rider 的 current_order_count = 0
时间 T2：派单把数据库里的 current_order_count 增到 1
时间 T3：资料请求把旧 rider 整条写回，可能又把计数写成 0

这叫“旧对象覆盖新数据”，也常称丢失更新。它与上一节的状态竞态相邻，但防法不同：这次重点不是检查状态，而是限制这条 SQL 的 SET 只能碰资料字段。

项目里怎样只更新需要的列？

在 RiderService.update 中，更新条件与修改字段是分开写的：

var update = Wrappers.<Rider>lambdaUpdate()
        .eq(Rider::getId, id)               // WHERE id = ?
        .set(Rider::getName, request.getName())
        .set(Rider::getPhone, request.getPhone());

if (request.getLatitude() != null) {
    update.set(Rider::getLatitude, request.getLatitude());
}

riderMapper.update(null, update);

eq 指定要更新哪名骑手；每个 set 指定本次允许修改哪个列。大致生成 UPDATE rider SET name=?, phone=? WHERE id=?，不会把数据库里最新的接单数和状态重写成请求对象里的旧值。MyBatis-Plus 官方文档说明，更新字段和条件可以通过 LambdaUpdateWrapper 构造，实体参数也可以省略，见条件构造器文档。

  • var 是 Java 编译器从右侧推断局部变量类型；仍是编译期确定的类型，不是动态类型。
  • Rider::getName 是类型安全的字段引用，重命名 Java 属性时 IDE 更容易发现引用。
  • update(null, update) 的第一个参数是实体对象；这里故意不给整条实体，只让 Wrapper 描述 SET 和 WHERE。
  • 坐标为 null 时没有调用 set，意思是“这次不改坐标”；当前接口因此不能用 null 清空坐标。

把两种方法放在一张对照表里

保护方式主要限制本项目例子挡住什么
条件更新WHERE 同时检查预期状态WHERE id=? AND status=1订单已变化，还拿旧状态继续操作
指定字段更新SET 只列出本次允许改的列SET name=?, phone=?保存旧实体时覆盖并发改动的其他列

一句话区分：条件更新管“现在还允不允许改”；指定字段更新管“这次到底改哪些列”。必要时二者可以同时使用：在 SET 中限定改动字段，在 WHERE 中限定 ID 与预期状态/版本。

边界：指定字段更新不是万能并发锁

如果两个请求同时修改同一个手机号，指定字段更新只能避免它们覆盖接单数等无关字段；它本身不决定哪个手机号请求应该胜出。相同字段冲突仍需要业务规则、唯一索引或额外的状态/版本条件。当前项目的骑手编号和手机号还有数据库唯一约束。

这轮新增的测试在证明什么？

shouldRejectStartWhenOrderChangesAfterInitialRead 和 shouldRejectCancelWhenDispatchWinsTheRace 模拟“第一次查询通过、最终条件更新返回 0”的情况，验证 Service 会拒绝旧操作。停用骑手的测试也模拟“最初看到空闲、正式停用前接单数已变化”。这些 Mockito 单元测试验证失败分支处理，不会真的制造数据库锁等待或测并发吞吐。
