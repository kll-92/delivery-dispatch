第十三课：这些测试到底在证明什么

本课只讲本轮新增的测试，不把单元测试当成真实并发压测。它们的目标是：把并发竞态下应该走的失败分支固定下来，防止以后改代码时悄悄破坏保护逻辑。

为什么要模拟，而不是每次真的开两个请求？

真实并发受机器、线程调度和时机影响：今天两个请求刚好撞上，明天可能没有撞上。这样的测试不稳定。单元测试把关键结果直接模拟出来，例如“第一次查到订单可开始，但最终条件 UPDATE 影响 0 行”，专门检查 Service 会不会正确拒绝。

测试类的四个角色

@ExtendWith(MockitoExtension.class)
class DeliveryOrderServiceTest {
    @Mock
    private DeliveryOrderMapper deliveryOrderMapper;

    @InjectMocks
    private DeliveryOrderService deliveryOrderService;
}
  • @Mock：创建一个假的 Mapper，不连接真实 MySQL；测试可以精确控制它返回什么。
  • @InjectMocks：创建真正要测试的 Service，并把上面的 Mock 依赖注入进去。
  • @ExtendWith(MockitoExtension.class)：让 Mockito 和 JUnit 5 在测试开始前自动准备这些对象。
  • @Test：标记一个独立的测试场景；Maven 或 IDEA 会执行它。

如何模拟“数据库条件更新失败”？

when(deliveryOrderMapper.selectById(1L))
        .thenReturn(order(1L, 0, null));
when(deliveryOrderMapper.cancelIfPending(1L, 0, 4))
        .thenReturn(0);

assertThrows(IllegalArgumentException.class,
        () -> deliveryOrderService.cancel(1L));

第一句模拟第一次查询看到订单仍是待派单；第二句模拟真正执行条件 UPDATE 时影响了 0 行，代表派单已经抢先改变了状态。最后一句要求 Service 抛出预期异常。这样测试的不是 SQL 本身，而是 Service 收到“最终判定失败”后有没有正确处理。

verify 在检查什么？

verify(deliveryOrderMapper).cancelIfPending(1L, 0, 4);
verifyNoMoreInteractions(deliveryOrderMapper);

verify 检查某个依赖方法确实被调用过，并且参数正确；verifyNoMoreInteractions 检查失败后没有偷偷继续执行其他 Mapper 操作。它相当于检查 Service 的“动作轨迹”，而不仅是最终返回值。

三个新增场景各自代表什么？

测试模拟的真实问题期望结果
shouldRejectStartWhenOrderChangesAfterInitialRead订单初读为已派单，但开始配送前状态已变化拒绝开始，不继续处理
shouldRejectCancelWhenDispatchWinsTheRace取消和派单竞争，派单先赢取消抛异常，不覆盖派单结果
shouldNotDisableRiderIfAnOrderWasClaimedAfterTheRead停用初读为空闲，但正式停用前骑手接到订单停用失败，不把骑手改成停用

它不能证明什么？

  • 不能证明真实 MySQL 行锁等待时间。
  • 不能证明 Redis、Docker 或 Stream 联调正常。
  • 不能给出 QPS、吞吐量或性能提升百分比。
  • 不能代替两个真实请求的端到端验收。

它能证明的是：当 Mapper 告诉 Service“条件已经不满足”时，代码会按预期返回错误，不会继续写错数据。

面试表达

我为状态竞态补了单元测试：模拟初始查询通过、条件更新返回 0 的场景，验证 Service 会拒绝过期操作。测试使用 Mockito 隔离数据库依赖，验证的是业务分支和 Mapper 交互；真实锁竞争和吞吐仍需要集成测试或并发验收。
