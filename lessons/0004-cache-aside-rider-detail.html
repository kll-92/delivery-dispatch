第二个实战问题：为什么要先查 Redis？

用户查看骑手 2 的详情时，如果每次都访问 MySQL，热门骑手会不断给数据库施加重复负担。我们要让 Redis 充当第一层的快速回答者。

查询流程（Cache Aside）

请求 GET /api/v1/riders/2
          ↓
Redis 里有 rider:detail:2？
  ├─有：反序列化为 Rider，直接返回
  └─没有：查 MySQL
                 ↓
             查不到：抛出“骑手不存在”
             查到：写入 Redis（TTL 10 分钟）后返回

修改流程

更新 MySQL 成功
       ↓
DEL rider:detail:2
       ↓
下次读取回填新缓存

为什么是“删缓存”而不是“立即更新缓存”？因为改了什么字段、要存哪个版本都会增加复杂度；先删后读的策略更简单、更常用。

下一步代码会出现的两个对象

  • StringRedisTemplate：负责调用 Redis。
  • ObjectMapper：将 Java 的 Rider 对象和 JSON 字符串互相转换。

直接问我：“缓存未命中后到底哪个方法查 MySQL？”或者“为什么不立即更新 Redis？”。
